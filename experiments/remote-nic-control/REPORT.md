# 固定本地单卡、只改变远端网卡集合

日期：2026-11-05。11.163.39.114 拉取 11.163.39.110；TE CUDA13 wheel 0.3.14。

## 方法

本地始终 MC_TE_FILTERS=mlx5_bond_0，device=mlx5_bond_0。
A：远端仅 bond_0；B：远端允许 bond_0–3、不指定 device。
两端 CPU NUMA 0 首次触页，诊断确认全部 cpu:0；每次传输 512 MiB，接收端先清零，完成后完整检查 0x5A。
两种负载：single 为一次 512 MiB READ；batch 为同一注册 buffer 上的 128 × 4 MiB READ。
源端两种配置各有一个独立进程及 512 MiB buffer；仅被测源进程承载本轮传输。

性能执行顺序 A-B-B-A，每个区段分别测两种负载并交替顺序。每个新拉取进程热身 8 次、测量 20 次，关闭逐分片日志。
每个配置/负载最终有两次独立进程运行、40 个正式样本。下表汇总这 40 个样本的中位耗时。
诊断运行每种组合额外执行一次，开启分片日志，独立于性能样本。

## 结果

| 负载 | 远端单卡中位 ms | 远端四卡中位 ms | 单卡有效 GB/s | 四卡有效 GB/s | 倍率 |
|---|---:|---:|---:|---:|---:|
| single | 11.469 | 9.451 | 46.81 | 56.81 | 1.214× |
| batch | 11.477 | 9.744 | 46.78 | 55.09 | 1.178× |

所有数据校验通过，无 NUMA 查询失败或 transport retry counter exceeded。
GB/s 为十进制应用有效字节数 / API 完成耗时，不是物理链路线速测量。

各区段中位 GB/s：

|---|---|---:|---:|
| 0 | A 单卡 | 46.87 | 46.81 |
| 1 | B 四卡 | 55.75 | 54.62 |
| 2 | B 四卡 | 57.33 | 55.32 |
| 3 | A 单卡 | 46.76 | 46.78 |

## 路径证据与解释

单卡诊断：本地 bond_0 ← 远端 bond_0，512 MiB。
四卡诊断：本地仍只有 bond_0，远端 bond_0–3 各承担 128 MiB；两种负载均如此。
因此本次排除了“更换本地网卡”作为提升的必要条件：只开放远端多卡就复现了约 18%–21% 的吞吐提升。
不能进一步断言具体是远端 NIC 队列、内存路径、QP 并行度还是网络路径改善；这些伴随端点数变化，需要额外硬件/连接观测才能分解。

## 限制与原始数据

两端计数器为宿主机全局计数，背景样本另存 background.json。
同节点不同源进程的物理内存页、端点和连接数量不完全相同；控制了 NUMA、大小、模式及本地卡，但尚未做微架构归因。
sysfs 对 bond_0 报告 400 Gb/sec；部分 API 有效吞吐高于其简单换算值，bond 逻辑设备到物理端口的速率口径尚未核实，因此不将应用吞吐直接解释为单物理端口线速。
不涉及 GPU buffer 或真实模型 KV 调度，未获取网络逐跳路由。

每次测量的 *.json 保存逐轮耗时和本机计数；*-remote-counters.json 保存远端计数；*.log 保存原始日志；summary.json 汇总结果及路径。

复现：在仓库根目录执行 `.venv/bin/python run_remote_nic_control.py`，然后 `.venv/bin/python summarize_remote_nic.py`。远端需已有同版本 nic_probe.py 和 .venv。
重跑会覆盖同名文件，先备份结果。本次启动的两个源进程已停止，probe-remote-*.json 不可复用。
