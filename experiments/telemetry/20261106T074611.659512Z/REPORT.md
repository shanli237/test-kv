## 工作负载

基线 2 秒，依次 single、batch、parallel，阶段间恢复 1 秒。
每阶段 2 轮热身 + 24 轮测量，每轮 256 MiB，全部数据逐字节校验通过，总有效 payload 19.5 GiB。
single 一个 256 MiB 调用；batch 一个含 64 × 4 MiB 请求的调用；parallel 四线程各调用一次 64 MiB READ。
事件总计 156 个 API 调用（含热身），全部开始/结束配对，返回成功。
峰值应用侧在途调用 4 个、在途字节 256 MiB。该指标不是硬件队列深度。

## 观察

1. 本地 bond_0 收流量与远端 bond_0 发流量呈相应突发，应用在途量和阶段时间可关联。
2. single/batch 正式样本的 API 中位耗时分别 5.823 / 5.838 ms；parallel 每个 64 MiB 调用中位 4.461 ms，不是四路合并的整轮延迟。图包含热身建连尖峰。
3. 远端 bond_0 的 rx_read_requests 增加 319488，与 19.5 GiB / 64 KiB 相符，是本轮 READ 分片流量的交叉证据；仍是全局硬件计数。
4. 其他端口有背景流量。观察到本地 bond_0 resp_cqe_error +768、resp_cqe_flush_error +765，以及 bond_2 rp_cnp_handled +76。所有应用传输和完整校验成功；未做 QP 归属/拆连接事件关联，因此不能将这些计数定性为本实验传输失败，也不能宣称设备无错误/拥塞。
5. 清零、Python 全量校验和阶段间隔导致流量空档；100 ms 平均曲线峰值约数 GB/s，不等于毫秒级传输期间的瞬时吞吐。
